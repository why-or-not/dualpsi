# dualpsi — 명부를 공개하지 않고 이중당적자를 찾는 도구

두 정당(예: 더불어민주당 측 **DP**, 조국혁신당 측 **RKP**)이 서로의 당원 명부를 넘기지 않고 **양쪽에 모두 등록된 사람만** 찾아냅니다. 양측이 합의한 **중개인**(선관위·공증인 등)이 계산을 중개하지만, 중개인도 이름은 한 명도 보지 못합니다.

- **PSI(비공개 교집합)**: ECDH 기반. 겹치지 않는 당원은 상대에게도 중개인에게도 드러나지 않습니다.
- **영지식 증명(DLEQ)**: 각 당이 상대 원소 전부에 같은 키를 빠짐없이 적용했음을 키를 드러내지 않고 증명합니다.
- **봉인 + 중개**: 2라운드 값은 중개인만 열 수 있게 봉인되고, 중개인이 매칭을 계산해 서명한 결과를 양측에 동시에 줍니다.
- **상호 재확인·수락**: 각 당은 받은 매칭 값을 자기 키로 다시 계산하고, 상대도 같은 결과를 수락했는지 확인한 뒤에만 결과를 확정합니다. 중개인이 가짜 매칭을 끼워 넣으면 한쪽이 거부하고, 그 거부가 다른 쪽에도 전달됩니다.
- **명부 사전 커밋 + 감사**: 명부를 해시(머클 루트)로 미리 고정하고, 남의 당원을 끼워 넣는 행위를 감사로 적발합니다.
- **두 단계 운영**: 1단계는 건수만, 2단계에서 명단(각 당은 자기 당원 중 해당자만).

> 참고 구현입니다. 독립 보안 검토 2회를 거쳐 지적 사항(아래 4절)을 반영했지만, 실제 명부에 쓰기 전에 별도 보안 감사와 법률 검토(민감정보 처리 근거, 결합 절차, 정당법상 처리 절차)를 받으시기 바랍니다.

## 1. 빠른 시작

```bash
pip install pynacl          # Python 3.9 이상, 의존성은 PyNaCl(libsodium) 하나
python -m dualpsi demo      # 가상 명부로 전체 절차 + 공격 4종 탐지 시연 (2코어 기준 약 1분 30초)
python -m pytest -q         # 테스트 69개
```

데모는 표기가 제각각인 두 가상 명부(UTF-8 / CP949, `+82 10-…`, `800102`, `홍 길동` 등)로 건수 모드 → 명단 모드 → 감사 → 공격 4종(값 조작, 떠보기, 명부 끼워넣기, 중개인의 결과 위조)을 실행하고 평문으로 대조한 정답과 결과가 같은지 확인합니다.

설치형으로 쓰려면 `pip install .` 후 `dualpsi <명령>`.

## 2. 참여자와 폴더

| 참여자 | 하는 일 |
|---|---|
| 각 당 실무자 | 자기 명부로 setup · round1 · round2 · finalize · confirm · audit-open |
| 중개인 (양측이 합의한 중립 기관) | hub-init · mediate(검증·매칭·결과 배포). 감사인을 겸할 수 있음 |
| 감사인 | audit-verify(감사 응답 검증, 실당원 증빙 대조) · verify-transcript |

| 폴더·파일 | 내용 | 취급 |
|---|---|---|
| `--work` 작업 폴더 | 서명키·비밀 시드·세션 키, 결과 명단 | **반출 금지**, 암호화 저장소 권장 |
| `--exchange` 교환 폴더 | `*.msg` 메시지 (명부 내용 없음) | 아래 표대로 주고받음 |
| 감사 응답 `*.json` | 감사 대상 레코드 원문 | **감사인에게만** |

## 3. 운영 절차 (권장)

### 0) 사전 합의
중개인, 파일 전달 수단, 세션 이름, 모드, 감사 건수(`--audit-k`), 목적 문구(`--purpose`), 두 자리 연도 기준(`--pivot-yy`, 기본 `(올해-16) % 100`)을 문서로 합의합니다. **양당의 round1 옵션이 한 글자라도 다르면 진행되지 않습니다.**

### 1) 준비

```bash
# 중개인
python -m dualpsi hub-init --work work_HUB --exchange xh --label HUB --name "중앙선거관리위원회"
# 각 당
python -m dualpsi setup --work work_DP --exchange xa --label DP --name "더불어민주당" --roster dp_members.csv
```

- `HUB.hub.msg` 는 양당에, `DP.setup.msg`·`RKP.setup.msg` 는 상대와 중개인에게 보냅니다(명부 내용 없음).
- 화면의 **서명키 지문**을 서로 전화나 서면으로 대조합니다.
- 중개인은 각 당이 커밋한 레코드 수를 공식 보고 당원 수와 비교해 둡니다(아래 '은닉·끼워넣기' 참고).

### 2) 1단계 — 건수만 확인 (세션 `phase1`)

```bash
# 각 당 (양당 동일 옵션)
python -m dualpsi round1 --work work_DP --exchange xa --session phase1 --mode count \
       --peer-fingerprint "6032 3DA7 8481 FA65 2A72 6414" --hub-fingerprint "6EFE D8F6 B796 004C 2AD1 257A"
#   → DP.phase1.round1.msg 를 상대와 중개인에게
python -m dualpsi round2 --work work_DP --exchange xa --session phase1
#   → DP.phase1.round2.msg 를 중개인에게 (봉인되어 있어 중개인만 열 수 있음)

# 중개인
python -m dualpsi mediate --work work_HUB --exchange xh --session phase1
#   → HUB.phase1.result.msg 를 양당에 동시에

# 각 당
python -m dualpsi finalize --work work_DP --exchange xa --session phase1
#   → 결과 검증 후 수락(또는 거부) 서명 DP.phase1.accept.msg 를 상대와 중개인에게
python -m dualpsi confirm  --work work_DP --exchange xa --session phase1
#   → 상대도 같은 결과를 수락했는지 확인하고 확정
```

결과: "정밀 일치 N건, 이름·생년월일 일치 M건". 누가 겹치는지는 **양당 모두 모릅니다**. 건수는 양당이 다시 셀 수 없어 중개인 계산을 믿은 값입니다. 대신 2단계를 확정할 때 도구가 1단계 건수와 2단계 매칭 수를 자동으로 대조해, 다르면 경고합니다.

### 3) 2단계 — 명단 산출 (세션 `phase2`)

같은 명령을 `--session phase2 --mode list` 로 반복합니다(명단 모드 기본 등급은 정밀만). 결과: `work_DP/sessions/phase2/result.csv`(confirm 후 생성, 그 전에는 `result.pending.csv`) — **우리 당원 중** 상대 당에도 있는 사람의 목록(등급, 이름, 생년월일, 전화, 원본 명부 줄 번호). 상대 당원 정보는 들어 있지 않습니다. 같은 setup(같은 커밋)으로 두 세션을 돌리므로 1단계와 2단계에 다른 명부를 쓸 수 없습니다.

### 4) 감사

```bash
# 각 당: 감사 응답을 만들어 감사인에게만
python -m dualpsi audit-open --work work_DP --exchange xa --session phase2 --challenge random  --out dp_random.json
python -m dualpsi audit-open --work work_DP --exchange xa --session phase2 --challenge matched --out dp_matched.json

# 감사인: 감사 범위는 감사인이 --challenge 로 정합니다(응답에 적힌 범위는 믿지 않음)
python -m dualpsi audit-verify --exchange xh --session phase2 --opening dp_matched.json --challenge matched \
       --evidence dp_evidence.csv --report dp_matched_report.json --worklist dp_check.csv
python -m dualpsi verify-transcript --exchange xh --session phase2 --hub-work work_HUB   # 전체 재계산
```

- 양당의 수락 메시지(`*.accept.msg`)가 모두 있어야 감사가 진행됩니다.
- 무작위 감사 위치는 양당이 1라운드에 커밋하고 2라운드에 공개한 난수로 정해져 어느 쪽도 고를 수 없습니다.
- 증빙 CSV는 입당원서·당비 기록 등 원 증빙에서 뽑은 목록입니다. 없으면 `--worklist` 로 수작업 확인합니다.
- 보고서(`--report`)에는 레코드가 없어 양당에 공유할 수 있습니다. `--worklist` 는 감사인 보관용입니다.

### 5) 마무리
각 당은 `result.csv` 의 자기 당원에게 연락해 본인이 소속을 정리하도록 합니다(처리 절차는 법률 검토). 감사가 끝나면 `destroy-key` 로 세션 키를 폐기하고, 작업 폴더는 합의한 기간 뒤 안전하게 삭제합니다.

### 파일 전달 요약

| 단계 | 보낼 파일 | 받는 사람 |
|---|---|---|
| hub-init | `HUB.hub.msg` | 양당 |
| setup | `{당}.setup.msg` | 상대, 중개인 |
| round1 | `{당}.{세션}.round1.msg` | 상대, 중개인 |
| round2 | `{당}.{세션}.round2.msg` | **중개인** (봉인됨) |
| mediate | `HUB.{세션}.result.msg` | 양당 (동시에) |
| finalize | `{당}.{세션}.accept.msg` (수락·거부 서명) | 상대, 중개인 |
| 감사 | `audit-open` 결과 JSON | **감사인만** |

## 4. 왜 중개인 구조인가 (검토 반영 내역)

처음 구현은 두 당이 2라운드 값을 직접 주고받는 2자 구조였습니다. 독립 검토에서 다음이 확인되어 바꿨습니다.

1. **떠보기 공격(치명)** — 한쪽이 1라운드에 자기 키를 쓰지 않은 값 H(추측)을 섞어 보내면, 상대가 돌려준 k_상대·H(추측) 을 상대의 1라운드 값과 비교해 **특정인이 상대 당원인지 몰래 조회**할 수 있었습니다. 이 조회는 교집합에 나타나지 않아 매칭 감사로도 잡히지 않습니다. 원소마다 "내 키로 만든 값"임을 증명하려면 해시 계산 자체를 회로로 증명(SNARK)해야 해 비현실적이므로, **2라운드 값을 중개인만 보게 하는 구조**로 바꿨습니다. 이제 떠보기로 얻는 정보가 없고, 끼워넣기는 반드시 양측에 보이는 매칭으로만 나타나 감사에서 드러납니다.
2. **감사 범위를 응답자가 정할 수 있던 문제(치명)** — 감사인이 응답에 적힌 감사 종류를 믿었기 때문에, 끼워 넣은 위치를 빼고 낸 응답이 통과할 수 있었습니다. 이제 감사인이 범위를 직접 정하고 다르면 거부합니다.
3. **키·난수 재사용(높음)** — 같은 세션을 다시 돌리거나 2라운드를 두 번 계산할 수 있었습니다. 이제 세션은 한 번만 시작되고 2라운드는 한 번만 계산되며, 감사 난수는 매번 새로 뽑습니다.

구조가 바뀌면서 건수 모드의 카나리·커밋 후 공개 단계는 필요 없어져 없앴습니다(중개인이 건수만 배포).

바뀐 구조에 대한 2차 검토에서는 위 세 가지가 해결된 것을 확인했고, 다음이 새로 나와 반영했습니다.

4. **한쪽만 통과하는 가짜 매칭(높음)** — 매칭 값 재확인은 양당이 서로 다른 식으로 하므로, 중개인이 한쪽 확인만 통과하는 가짜 쌍을 넣으면 그쪽은 받아들이고 다른 쪽만 거부했습니다. 게다가 가짜 쌍은 실제 당원끼리 묶여 감사로도 드러나지 않았습니다. 이제 각 당은 수락·거부를 서명해 서로 주고받고, **양쪽이 같은 결과를 수락한 경우에만 확정(confirm)**되며, 감사도 그때만 진행됩니다.
5. **건수 모드의 건수는 검증할 수 없음(중간)** — 양당이 다시 세게 하려면 떠보기가 다시 가능해지므로, 건수는 중개인을 믿는 값으로 명시하고, 같은 명부로 한 명단 세션과 자동 대조해 부풀리기를 드러내게 했습니다.
6. **결과가 우리가 보낸 2라운드에 대한 것인지 미확인(낮음)** — 확인하도록 고쳤습니다.

## 5. 무엇을 보장하고, 무엇은 보장하지 못하나

### 보장하는 것

| 위협 | 대응 | 수준 |
|---|---|---|
| 상대 당이 겹치지 않는 당원까지 알아냄 | 상대에게 가는 값은 상대 키 없이 풀 수 없고, 2라운드는 중개인에게 봉인 | 암호학적 (중개인 비공모 전제) |
| 중개인이 당원 이름을 알아냄 | 중개인은 두 키를 모두 알아야 풀리는 값만 봄 | 암호학적 (감사 응답 제외) |
| 떠보기(키를 안 쓴 원소로 몰래 조회) | 돌려받는 값이 없어 얻는 정보 없음. 감사 표본에 걸리면 불일치로 드러남 | 암호학적 (중개인 비공모 전제) |
| 한 당이 계산을 조작해 특정인을 숨기거나 끼워 넣음 | 중개인이 배치 DLEQ 증명 검증 | 암호학적(확정) |
| 중개인이 가짜 매칭을 만들어 냄 | 양당이 각자 매칭 값을 자기 키로 재계산하고, 서로의 수락을 확인한 뒤에만 확정 | 암호학적(확정) |
| 남의 당원을 자기 명부에 끼워 넣기 | 양측에 똑같이 보이는 매칭이 되어 매칭 감사에서 전원 적발, 대량이면 무작위 감사로도 | 사후 적발 |
| 1단계·2단계에 다른 명부 사용 | 머클 루트로 사전 고정, 도구가 매번 명부 해시 확인, 감사는 항상 이 루트로 검증 | 도구 강제 + 감사 |
| 감사 위치를 유리하게 고르기 | 양당 커밋-공개 난수로 결정, 범위는 감사인이 결정 | 암호학적 |
| 결과를 먼저 받고 중단 | 중개인이 양당에 동시 배포 | 운영 |
| 보낸 메시지를 부인 | 모든 메시지 Ed25519 서명 | 암호학적 |

### 보장하지 못하는 것 (반드시 읽어 주세요)

1. **자기 당원을 일부러 빼는 것(은닉)은 막을 수 없습니다.** 어떤 보안 계산이든 무엇을 입력할지는 당사자가 정합니다. 커밋한 레코드 수를 공식 당원 수와 대조하고(`--peer-max-records`) 무작위 감사로 억제할 뿐입니다.
2. **중개인은 신뢰해야 합니다.**
   - 중개인이 한 당과 공모해 2라운드 값을 넘기면, 그 당은 떠보기를 할 수 있게 됩니다(자기 1라운드 원소 수만큼). 건수 모드에서는 공모한 당이 겹치는 자기 당원이 누구인지도 알 수 있습니다.
   - 중개인은 매칭을 **빼먹을** 수 있고, 양당은 이를 스스로 확인하지 못합니다(만들어 내는 것은 막힘).
   - 건수 모드의 건수는 중개인 계산을 믿어야 합니다. 1단계와 2단계를 같은 명부로 돌리면 confirm 때 자동 대조되어 부풀리기·축소가 드러나지만, 2단계에서도 똑같이 빼먹으면 드러나지 않습니다.
   - 분쟁 시 중개인 작업 폴더로 제3자가 `verify-transcript --hub-work` 를 돌려 전체를 재계산할 수 있습니다.
3. **실당원인지는 결국 원 증빙(입당원서·당비 기록)으로 확인합니다.** 처음 설명드린 '원소 전체에 대한 ZK 멤버십 증명' 대신 커밋 + 감사 방식을 택한 이유가 이것입니다. 원소 전체 ZK 증명은 해시 계산을 회로로 증명해야 해 수백만 건이면 비용이 매우 크고, 그렇게 해도 "커밋한 명부와 일치"까지만 보장할 뿐 그 명부가 진짜인지는 증명하지 못합니다.
4. **감사인은 무작위 감사 건(기본 200건)과 매칭 건의 레코드를 봅니다.** 감사인과 한 당이 공모하면 그 레코드가 넘어갈 수 있습니다.
5. **드러나는 메타데이터**: 각 당의 (중복 제거 후) 명부 크기, 등급별 원소 수(전화번호 보유자 수), 교집합 크기.
6. **명단 모드의 후보(loose) 등급은 동명이인을 드러냅니다.** 우리 당원과 이름·생년월일이 같은 상대 당의 **다른 사람**이 있다는 사실이 노출됩니다. 그래서 명단 모드 기본값은 정밀 등급만이고, 후보 등급은 1단계 건수 모드에서 규모만 보는 것을 권장합니다.
7. **표기 차이는 놓칩니다.** 개명, 오타, 생년월일 오입력은 정규화로 해결되지 않습니다.
8. **키 폐기**는 상태 파일에서 지우는 것입니다. 작업 폴더 전체를 암호화된 저장소에서 운영하세요.

### 무작위 감사 건수와 탐지 확률

부정 원소 비율이 f 일 때 무작위 k건 감사로 하나 이상 적발할 확률 1 − (1 − f)^k:

| 부정 비율 | k=100 | k=200 (기본) | k=500 | k=1000 |
|---|---|---|---|---|
| 0.2% | 18.1% | 33.0% | 63.2% | 86.5% |
| 0.5% | 39.4% | 63.3% | 91.8% | 99.3% |
| 1% | 63.4% | 86.6% | 99.3% | ≈100% |
| 2% | 86.7% | 98.2% | ≈100% | ≈100% |
| 5% | 99.4% | ≈100% | ≈100% | ≈100% |

매칭된 원소는 비율과 무관하게 **매칭 감사로 100% 확인**됩니다.

## 6. 입력 명부 형식

- CSV, 인코딩 자동 판별(UTF-8 / CP949·EUC-KR). 엑셀에서 저장한 파일 그대로 쓸 수 있습니다.
- 열 이름 자동 인식: 이름(이름·성명·성함·당원명), 생년월일(생년월일·생일·출생일·DOB), 휴대전화(휴대전화·휴대폰·연락처·전화번호). 안 맞으면 `--col-name --col-birth --col-phone`.
- 정규화 규칙(버전 `kr-v1`, 양측 동일해야 함):

| 항목 | 규칙 | 예 |
|---|---|---|
| 이름 | 괄호 주석 제거, 문자 외(공백·기호·숫자) 제거, NFC, 대문자 | `홍 길동(서울)` → `홍길동` |
| 생년월일 | 8자리 / 6자리(연도 기준 적용) / 구분자 / `년월일` / 성별자리 포함 형식 | `80.1.2`, `1980년 1월 2일`, `800102-1` → `19800102` |
| 전화 | 숫자만, `+82`→`0`, 엑셀이 지운 앞자리 0 복원 | `+82 10-1234-5678`, `1012345678` → `01012345678` |

- 생년월일을 읽을 수 없는 행은 제외되고 `work/rejects.csv` 에 줄 번호가 남습니다.
- 전화번호가 없거나 읽을 수 없는 사람은 후보 등급으로만 비교됩니다.
- 같은 사람이 여러 줄이면 하나로 합칩니다(결과에 줄 번호가 모두 표시됨).

## 7. 프로토콜 요약

```
        DP (키 a)                     중개인 HUB                     RKP (키 b)
setup   R_A, n_A  ──────────────────────▶ ◀────────────────────── R_B, n_B
                  ◀──────────── 서명키 · 봉인용 공개키 ────────────▶
        sid = H(setup_A, setup_B, HUB, 세션 파라미터)
round1  U_A = { a·H_sid(e) } ─────────▶ (사본) ◀───────── U_B = { b·H_sid(e') }   (서로 교환)
round2  봉인[ D_B = a·U_B + 배치 DLEQ ] ──▶     ◀── 봉인[ D_A = b·U_A + 배치 DLEQ ]
mediate                         증명 검증 → D_A[i] == D_B[j] 인 쌍
result  ◀──────────── 서명된 결과 (명단: 위치 쌍+값 / 건수: 건수) ────────────▶
finalize 값 v 를 자기 키로 재계산: DP는 v == a·U_B[j], RKP는 v == b·U_A[i] → 수락·거부 서명 교환
confirm  양쪽이 같은 결과를 수락했을 때만 확정 (둘 다 통과해야 b·U_A[i] == a·U_B[j], 즉 진짜 매칭)
```

- **군**: libsodium edwards25519의 소수 위수 부분군. 받은 점은 모두 정규 인코딩·주 부분군 소속을 검사합니다. 해시-투-군은 Elligator2 사상 두 개의 합입니다(PyNaCl이 Ristretto255를 노출하지 않아 이 방식을 썼고, 부분군 검사 덕분에 안전성은 같습니다).
- **배치 DLEQ**: 계수 c_i 를 전체 입·출력의 해시로 정한 뒤 Σc_i·U_i 와 Σc_i·D_i 에 대한 Chaum–Pedersen 증명. 원소 하나라도 다르면 통과 확률이 약 2⁻²⁵²입니다.
- **봉인**: 2라운드는 중개인의 X25519 공개키로 SealedBox 암호화하고, 안쪽 내용에도 세션 ID와 대상 1라운드 ID를 넣어 헤더와 묶습니다.
- **감사 응답**: 레코드 + 솔트 + 머클 경로(사전 커밋한 명부에 있었음) + DLEQ(1라운드 값이 그 레코드의 해시에 커밋한 키를 적용한 것임). 키는 드러나지 않습니다.

## 8. 성능 (실측)

2 vCPU, 명단 모드, 정밀+후보 2등급(원소 수 ≈ 레코드 수 × 2), DP 10만 명(원소 20만) 대 RKP 4만 명(원소 8만):

| 단계 | DP | RKP | 중개인 |
|---|---|---|---|
| setup / hub-init | 약 1초 | 약 1초 | 즉시 |
| round1 | 19.3초 | 7.8초 | |
| round2 | 7.9초 | 19.8초 | |
| mediate (양쪽 증명 검증 + 매칭) | | | 31.4초 |
| finalize (매칭 값 재확인) | 1.0초 | 0.6초 | |

- 대략 CPU 시간: 각 당은 **자기 원소 수 × 0.19ms + 상대 원소 수 × 0.2ms**, 중개인은 **전체 원소 수 × 0.22ms**. 코어 수만큼 나눠집니다(`--workers`, 기본 CPU 수). 추정 예: 100만 명 대 30만 명, 정밀 1등급, 8코어 → 각 당 약 30초, 중개인 약 40초.
- 메시지 크기는 원소당 32바이트(100만 원소 ≈ 32MB). 메모리는 위 실측(세 참여자를 한 프로세스에서 실행)에서 최대 약 270MB였고, 원소 100만 개당 1GB 이내로 잡으면 넉넉합니다.
- 라이브러리를 직접 호출하는 스크립트는 macOS·Windows에서 `if __name__ == "__main__":` 가드가 필요합니다(병렬 프로세스가 spawn 방식이라서). CLI(`python -m dualpsi`)는 상관없습니다.
